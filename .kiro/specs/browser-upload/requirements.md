# Requirements Document

## Introduction

The Browser Upload feature adds a web-based document upload interface to the Sports Experience Guidelines repository. It provides a browser UI (integrated into the existing Express dashboard) where users can upload source documents via drag-and-drop or file picker, preview the converted output, adjust the target location and content, and see validation results — all before committing the document to the repository.

This feature reuses the existing CLI-based import pipeline (ContentExtractor, TemplateEngine, DocumentTypeInferrer, ImportValidation, manifest update) and exposes it through HTTP endpoints and a browser frontend.

## Glossary

- **Upload_Server**: The Express.js HTTP server that hosts the upload API endpoints, integrated into the existing dashboard server (`tools/src/dashboard.ts`)
- **Upload_UI**: The browser-based single-page interface for uploading, previewing, and confirming document imports
- **Import_Pipeline**: The existing document import orchestration (ContentExtractor → DocumentTypeInferrer → TemplateEngine → ImportValidation → persistence) implemented in `tools/src/import-service.ts`
- **Preview_Panel**: The section of the Upload_UI that displays the converted markdown output and validation results before the user confirms or rejects
- **Source_Document**: A file uploaded by the user in PDF, plain text, or markdown format
- **Target_Document**: The standardised markdown file generated by the Import_Pipeline from the Source_Document
- **Validation_Result**: The combined output of frontmatter, structure, and naming validation checks performed on a Target_Document

## Requirements

### Requirement 1: File Upload via Browser

**User Story:** As a guidelines contributor, I want to upload a source document through my browser, so that I can import documents without using the command line.

#### Acceptance Criteria

1. THE Upload_UI SHALL provide a drag-and-drop zone that accepts file drops from the user's file system and displays a visual highlight when a file is dragged over the zone
2. THE Upload_UI SHALL provide a file picker button that opens the browser's native file selection dialog
3. WHEN a user drops a single file onto the drag-and-drop zone, THE Upload_UI SHALL initiate the upload to the Upload_Server
4. WHEN a user selects a file via the file picker, THE Upload_UI SHALL initiate the upload to the Upload_Server
5. THE Upload_UI SHALL accept files with extensions `.pdf`, `.txt`, `.text`, `.md`, and `.markdown`
6. IF a user attempts to upload a file with an unsupported extension, THEN THE Upload_UI SHALL reject the file before transmission and display an error message listing the supported formats
7. IF a user attempts to upload a file exceeding 20 MB, THEN THE Upload_UI SHALL reject the file before transmission and display an error message stating the maximum file size
8. IF a user drops multiple files onto the drag-and-drop zone, THEN THE Upload_UI SHALL reject the drop and display an error message indicating that only one file may be uploaded at a time
9. IF a user attempts to upload a file of 0 bytes, THEN THE Upload_UI SHALL reject the file and display an error message indicating that the file is empty

### Requirement 2: Server-Side Upload Processing

**User Story:** As a guidelines contributor, I want uploaded files to be processed through the existing import pipeline, so that converted documents follow the same standards as CLI-imported ones.

#### Acceptance Criteria

1. WHEN the Upload_Server receives an uploaded file, THE Upload_Server SHALL invoke the Import_Pipeline extraction stage to produce ExtractedContent
2. WHEN extraction completes, THE Upload_Server SHALL invoke the DocumentTypeInferrer to determine the document type and confidence level
3. WHEN type inference completes, THE Upload_Server SHALL invoke the TemplateEngine to generate a Target_Document
4. WHEN generation completes, THE Upload_Server SHALL invoke the import validation to produce a Validation_Result containing categorised errors (frontmatter, structure, naming)
5. WHEN all pipeline stages complete successfully, THE Upload_Server SHALL return the generated markdown, suggested path, suggested filename, inference confidence level, and Validation_Result to the Upload_UI within 30 seconds of receiving the upload
6. IF extraction fails due to unreadable content, THEN THE Upload_Server SHALL return an error response indicating the failure reason and the pipeline stage at which it occurred
7. IF the TemplateEngine or validation stage fails due to an unexpected error, THEN THE Upload_Server SHALL return an error response indicating the failing stage and a message describing the cause
8. IF the DocumentTypeInferrer returns low confidence, THEN THE Upload_Server SHALL include the confidence level and the list of available document types in the response so the Upload_UI can prompt the user to select a type

### Requirement 3: Document Preview

**User Story:** As a guidelines contributor, I want to preview the converted document in the browser before saving, so that I can verify the output meets my expectations.

#### Acceptance Criteria

1. WHEN the Upload_Server returns a successful processing result, THE Upload_UI SHALL render the generated markdown in the Preview_Panel within 2 seconds of receiving the response
2. THE Preview_Panel SHALL display the frontmatter fields as labeled key-value pairs, showing each field name alongside its value on a separate line
3. THE Preview_Panel SHALL display the markdown body converted to styled HTML with rendered headings, lists, tables, and inline formatting
4. THE Preview_Panel SHALL display the suggested target path and filename as distinct labeled text fields
5. WHEN the Validation_Result contains errors, THE Preview_Panel SHALL display each validation error indicating the field or section it relates to and the nature of the issue
6. IF the generated markdown body is empty, THEN THE Preview_Panel SHALL display an informational message indicating that no content was extracted from the Source_Document

### Requirement 4: Target Location Adjustment

**User Story:** As a guidelines contributor, I want to adjust the suggested file path and filename before saving, so that I can place the document in the correct location.

#### Acceptance Criteria

1. THE Upload_UI SHALL display the suggested path and filename as separate editable text fields in the Preview_Panel, each with a maximum input length of 256 characters
2. WHEN a user modifies the target path or filename and moves focus away from the field, THE Upload_UI SHALL send the updated values to the Upload_Server for re-validation
3. WHEN the Upload_Server receives updated path values, THE Upload_Server SHALL run naming validation on each folder segment and the filename and return an updated Validation_Result
4. IF the user-provided filename does not follow kebab-case rules (pattern: [a-z0-9]+(-[a-z0-9]+)*.md, maximum 64 characters), THEN THE Upload_UI SHALL display a naming validation error identifying the filename field
5. IF any folder segment in the user-provided path does not follow kebab-case rules (pattern: [a-z0-9]+(-[a-z0-9]+)*, maximum 64 characters per segment), THEN THE Upload_UI SHALL display a naming validation error identifying the invalid folder segment
6. IF the user-provided path resolves to a location outside the repository root, THEN THE Upload_Server SHALL reject the path and return a validation error
7. IF the user clears the path or filename field, THEN THE Upload_UI SHALL display a validation error indicating that the field is required

### Requirement 5: Document Type Override

**User Story:** As a guidelines contributor, I want to override the inferred document type when the automatic inference is uncertain, so that the correct template is applied.

#### Acceptance Criteria

1. THE Upload_UI SHALL display the inferred document type and its confidence level after processing
2. WHEN the inference confidence is low, THE Upload_UI SHALL prompt the user to select a document type from the available options: overview, principles, patterns, research, decisions, guidelines, examples
3. WHEN the user selects a different document type, THE Upload_UI SHALL send the override to the Upload_Server for re-generation
4. WHEN the Upload_Server receives a document type override, THE Upload_Server SHALL re-run the TemplateEngine with the new type and return an updated Target_Document and Validation_Result
5. WHEN the inference confidence is medium or high, THE Upload_UI SHALL allow the user to manually change the document type from the available options without prompting

### Requirement 6: Metadata Override

**User Story:** As a guidelines contributor, I want to override inferred metadata fields (owner, subdomain, experience area), so that the frontmatter accurately reflects the document's intended context.

#### Acceptance Criteria

1. THE Upload_UI SHALL display editable fields for owner, subdomain, and experience area pre-populated with inferred values, each accepting a maximum of 100 characters
2. WHEN the user modifies any metadata field, THE Upload_UI SHALL send the updated overrides to the Upload_Server for re-generation
3. WHEN the Upload_Server receives metadata overrides, THE Upload_Server SHALL re-run the TemplateEngine with the overrides and return an updated Target_Document and Validation_Result
4. IF any metadata field is left empty by the user, THEN THE Upload_UI SHALL display a validation error indicating that the field is required

### Requirement 7: Save Confirmation

**User Story:** As a guidelines contributor, I want to explicitly confirm saving the document, so that no files are written to the repository without my approval.

#### Acceptance Criteria

1. THE Upload_UI SHALL provide a Save button that is enabled only when the Validation_Result contains zero errors
2. WHEN the user clicks Save, THE Upload_UI SHALL send a save request to the Upload_Server with the final target path and filename
3. WHEN the Upload_Server receives a save request, THE Upload_Server SHALL write the Target_Document to the specified path and update the manifest
4. WHEN persistence succeeds, THE Upload_Server SHALL return a success response containing the saved file path and manifest update status
5. WHEN persistence succeeds, THE Upload_UI SHALL display a success confirmation with the saved file path
6. IF persistence fails, THEN THE Upload_Server SHALL return an error response indicating the failure reason
7. IF the Upload_UI receives a persistence error response, THEN THE Upload_UI SHALL display the error message and keep the Save button enabled for retry
8. THE Upload_UI SHALL provide a Discard button that cancels the import without writing any files
9. WHEN the user clicks Discard, THE Upload_UI SHALL return to the initial upload state with the drag-and-drop zone
10. WHILE a save request is in progress, THE Upload_UI SHALL disable the Save button until the response is received

### Requirement 8: Validation Display

**User Story:** As a guidelines contributor, I want to see all validation issues clearly in the browser, so that I can understand and address problems before saving.

#### Acceptance Criteria

1. THE Upload_UI SHALL group validation errors by category: frontmatter errors, structure errors, and naming errors
2. WHEN the Validation_Result contains errors, THE Upload_UI SHALL display the total error count in a badge adjacent to the Save button
3. THE Upload_UI SHALL display validation errors inline alongside the relevant section of the Preview_Panel where applicable
4. IF a validation error cannot be associated with a specific preview section, THEN THE Upload_UI SHALL display it in a summary list at the top of the validation area
5. WHEN all validation errors are resolved through path or metadata adjustments, THE Upload_UI SHALL enable the Save button and hide the error count badge

### Requirement 9: Upload Progress Feedback

**User Story:** As a guidelines contributor, I want to see upload and processing progress, so that I know the system is working on my document.

#### Acceptance Criteria

1. WHEN a file upload begins, THE Upload_UI SHALL display a progress indicator showing that the file is being uploaded
2. WHEN the file has been uploaded and processing begins, THE Upload_UI SHALL display a status message indicating that conversion is in progress
3. WHEN processing completes successfully, THE Upload_UI SHALL transition to the preview state
4. WHILE processing is in progress, THE Upload_UI SHALL continue displaying the progress indicator with no client-side timeout
5. IF the Upload_Server returns an error during processing, THEN THE Upload_UI SHALL hide the progress indicator and display the error message with an option to retry the upload

### Requirement 10: Integration with Existing Dashboard

**User Story:** As a guidelines contributor, I want to access the upload interface from the existing dashboard, so that I have a unified experience for managing guidelines.

#### Acceptance Criteria

1. THE Upload_Server SHALL register its API endpoints on the existing Express application instance used by the dashboard
2. THE Upload_UI SHALL be accessible via a dedicated route (`/upload`) on the dashboard
3. THE Upload_UI SHALL include navigation that allows returning to the main dashboard view
4. THE dashboard header SHALL include a navigation link to the Upload_UI
